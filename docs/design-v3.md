# アサエール 開発設計書 v3（ラウンド3: 公開リールフィード）2026-11-28

前提：ラウンド2（Supabase差し替え・2端末対応）が完了していること。本書は本人の案（2026-11-28）「応援する側が他の人の夢を見られるよう、公開OKの夢をリール形式で流す」を設計に落としたもの。流す範囲は本人の決定により「公開OKの夢すべて」。

## 1. 目的と検証仮説
- 応援する側の入口を作る：リンクを受け取った人だけでなく、アプリを開いた人が誰かの夢に出会って応援できる
- 仕様書 §12 の未検証仮説「知らない人からの応援でも嬉しいか？」を検証できる状態にする

## 2. 公開の仕組み（プライバシー前提）
- 目標登録に「みんなに公開する」チェックを追加する。**デフォルトはOFF**（リンク共有のみ）。ONにした夢だけがフィードに流れる
- 公開される項目はニックネーム／目標タイトル／詳細／起床予定だけ。メッセージ本文や本人用URLは公開されない
- 本人は後から公開を取り下げられる（受信画面に公開ON/OFFの切替を置く）
- 起床予定時刻を過ぎた夢は、公開ONでもフィードに流さない（役目を終えた夢を晒し続けない）

## 3. DB変更（SQLはラウンド3開始時に Muse が作成）
- `asayell_goals` に `is_public boolean not null default false` を追加
- `asayell_create_goal` に引数 `p_is_public` を追加
- 新RPC `asayell_list_public_goals(p_limit int)`：`is_public = true かつ wake_at > now()` の夢をランダム順で返す。返すのは nickname / title / detail / wake_at / support_token / 応援件数。support_token は応援投稿に必要な公開情報なので含めてよい
- 新RPC `asayell_set_public(p_owner_token, p_is_public)`：本人が公開を取り下げ／再公開できる
- 新RPC `asayell_hide_message(p_owner_token, p_message_id)`：本人が受け取ったメッセージを隠せる（status='hidden'）。公開化に伴う最低限の自衛手段として F07 の簡易版を兼ねる

## 4. 画面
- 新ルート `/feed`：縦スワイプのリール（CSS の scroll-snap で1件ずつ止まる）。スマホ全画面が前提
  - カード表示：ニックネーム、目標タイトル、詳細、起床予定（例「明日 6:30 起床」）、届いている応援の件数
  - 「応援する」ボタン → その夢の応援画面 `/s/:supportToken` へ遷移（既存の投稿導線をそのまま使う）
  - フィードが空のときは、空であることを正直に表示し、自分の夢を登録する導線を出す（ダミーの夢を流さない＝応援の偽造と同じ考え方）
- 導線：トップ画面（登録画面）に「みんなの夢を見る」リンクを置く。受信画面からも辿れるようにする
- データ取得は `AsayellRepository` に `listPublicGoals` を追加して経由する（設計v1のデータ層分離を維持）。localStorage モードでは自分の端末の公開夢だけが対象になる（制約として明記）

## 4.5 共通ナビゲーションとプロフィール（2026-11-28 本人指示で追加）
- 主要3画面を下部固定のナビゲーションバーで切り替える（スマホ前提。アイコン＋短いラベル）
  - **投稿**：目標登録画面（現行の `/`）
  - **みんなの夢**：公開リール `/feed`
  - **プロフィール**：`/me`（新規）
- プロフィール画面の内容（アカウント登録は作らない。本人確認は owner_token を端末に保持することで代替する）
  - 自分の夢の一覧：目標タイトル、起床予定、届いた応援の件数、公開ON/OFFの切替
  - 各夢の共有リンク（応援URL）と受信画面への導線
  - 夢を登録したときに、クライアントが owner_token を端末内（localStorage）に控えておき、プロフィールで自分の夢を引けるようにする。控えが無い端末ではプロフィールは空表示にし、本人用URLから辿れる従来導線は残す
- 応援画面 `/s/:supportToken` は、リンクを受け取った外部の人向けなのでナビゲーションバーは出さない（応援に集中してもらう）
- リール画面ではナビを下部に重ねて表示し、カードの「応援する」ボタンが隠れない位置に置く

## 5. 荒らし・安全面の扱い
- 公開はオプトイン＋起床後は自動で流れなくなる＋いつでも取り下げ可能、の3点で一次防御
- 受け取る側は hide_message で個別に隠せる
- 通報機能と管理者による全体削除は今回の範囲外（本格公開の前に別途設計する）。ただしピッチ等で不特定多数にURLを配る場合は、その前に通報導線の追加を検討する

## 6. 受入条件
- 公開OFFの夢がフィードに出ないこと。起床時刻を過ぎた夢が出ないこと
- フィードから応援を投稿し、相手の受信画面に届くこと（2端末）
- 公開の取り下げが即フィードに反映されること
- メッセージを隠すと受信画面に出なくなること
- 下部ナビから投稿／みんなの夢／プロフィールの3画面を行き来でき、プロフィールに自分の夢と応援件数が正しく出ること
- テスト・lint・build 合格

## 7. 評価ルーブリック
設計v1 §9 と同一配点・合格条件を踏襲。不合格条件に「公開OFFまたは起床済みの夢がフィードに出る」「フィード経由で本人用情報（owner_token、メッセージ本文）が取得できる」を追加する。

## 8. Issue分解（案）
- R3-01: DB拡張（is_public、list/set_public/hide_message のRPC）と登録画面の公開チェック＋受信画面の公開切替・非表示操作
- R3-02: リール画面 `/feed` と導線
- R3-03: 下部ナビゲーションバー（投稿／みんなの夢／プロフィール）とプロフィール画面 `/me`（自分の夢一覧・公開切替・共有導線、owner_token の端末控えを含む）
- R3-04: 統合テスト（公開→フィード→応援→受信の2端末通し）と公開確認
