# アサエール 開発設計書 v1（確定版・2026-11-28）

正本仕様：Startup Weekend 富士 4th プロトタイプ開発仕様書 v0.1（2026-11-27、`~/workspace/user/files/261127.pdf`）。本書はGAD（GitHub Issue駆動AI開発）で開発するための確定プロンプトであり、仕様書と矛盾する場合は仕様書の「価値の中心（実在する人からの応援）」を優先する。

## 0. 本ラウンドの決定事項（2026-11-28 本人決定）
- データ保存は **localStorage のみ**でP0を先行する。Supabase連携は次ラウンド。
- 対象はP0必須＋低コストなP1の一部（URL分離・解禁前非表示）。F07管理者削除・F08外部通知は対象外。

## 1. プロダクト概要
- 名前：アサエール（ASAYELL）。「誰かのエールが、明日を楽しみに変える」
- 対象：朝起きるのが辛い人（当初想定は会社員）
- コア体験：夢・目標と起床予定時刻を登録 → 応援募集URLを共有 → 仲間が応援メッセージを投稿 → 翌朝、起床時刻以降に本人専用URLで1通ずつ読む
- アサエールは目覚まし時計ではない。アラーム機能は作らない。

## 2. 技術構成
- React 19 + TypeScript（Vite）+ PWA不要（今回は素のWebアプリ）。公開は GitHub Pages（mainマージ＝即公開、計算無双と同方式）
- ルーティング：react-router 等のライブラリ追加は最小限にし、軽量な実装を優先（履歴APIベースで可）
- **データ層の抽象化（必須）**：UIは `AsayellRepository` インターフェース越しにのみデータへアクセスし、実装は `LocalStorageRepository` とする。次ラウンドで Supabase 実装へ差し替え可能にする（UI変更なしで差し替えできることが受入条件）
- テスト：Vitest。lint・build が CI（GitHub Actions: PRで test/lint/build）で通ること

## 3. 画面とルート
| ルート | 画面 | 内容 |
|---|---|---|
| `/` | トップ／目標登録（画面①） | ニックネーム、夢・目標・楽しみ（タイトル）、詳細（任意）、起床予定時刻、登録ボタン |
| `/share/:goalId` | 共有画面 | 「応援募集URLをコピー」「本人専用の受信URLを開く」ボタン |
| `/s/:supportToken` | 応援投稿（画面②） | 相手の目標表示、応援者名（任意）、メッセージ本文、投稿ボタン。投稿後は「翌朝に届きます」を表示。**他の応援は見られない** |
| `/o/:ownerToken` | 翌朝の受信（画面③） | 朝の挨拶、届いた件数、メッセージを1通ずつ表示＋「次へ」。解禁前は本文を隠す |

## 4. データモデル（localStorage）
- goal: `goal_id`（UUID）/ `nickname`（20文字以内）/ `title`（100文字以内）/ `detail`（300文字以内・任意）/ `wake_at`（次の朝の日時、Asia/Tokyo）/ `support_token` / `owner_token`（いずれも推測困難なランダム文字列で別々に発行）
- message: `message_id` / `goal_id` / `sender`（任意）/ `body`（150文字以内）/ `created_at` / `status`（visible固定でよい）
- 保存キーには接頭辞 `asayell:` を付ける

## 5. 機能要件（本ラウンドの範囲）
- F01 登録：ニックネーム・目標・起床予定時刻を登録し保存できる（バリデーション：空欄は送信不可、文字数上限）
- F02 URL発行：登録後、応援募集URLと本人専用URLを発行する（ルート分離がそのまま担保）
- F03 応援投稿：応援者がメッセージを投稿し、「翌朝に届く」と確認表示する
- F04 受信：朝の受信画面に応援メッセージを1通ずつ表示できる
- F05 解禁制御：`wake_at` より前は本文を見せない（件数の表示は可）。「明日の朝にエールが届きます」と案内する
- F06 デモモード：受信画面に「デモ：翌朝を体験する」導線を用意し、時刻を待たずに解禁状態を再現できる（デモであることが画面上で分かる表示にする）
- 0件の朝：人からの応援を偽造せず、「今日も自分のペースで」等の固定メッセージのみ表示する
- 対象外：F07 管理者削除、F08 外部通知、AI自動応援、認証、目標の公開一覧・検索

## 6. localStorage前提の制約（明示）
- データは登録したブラウザ内にのみ存在する。別端末の応援者は、**同じ端末で応援画面を開く**形で体験する（ピッチデモ・ヒアリングはこの前提で運用）
- 受け入れテスト T02（別端末投稿）・T06 のサーバー面は次ラウンド（Supabase差し替え時）に持ち越す。本ラウンドのT06は「応援URLから受信画面の本文が読めない」ルート分離で確認する

## 7. デザイン方針
- スマートフォン優先。デザインキーワードは「朝の明るさ・優しさ・安心感」（朝の光を思わせる淡いグラデーション、角丸、余白広め）
- 文言は優しく、責めない。0件・未解禁でも前向きな表現にする
- 入力は最小限。長い入力を求めすぎない

## 8. Issue分解案（依存順）
- A-00 基盤：プロジェクト雛形、ルーティング、データ層（インターフェース＋localStorage実装）、デザイン基盤、CI
- A-01 目標登録（F01）＋共有画面（F02）※A-00に依存
- A-02 応援投稿（F03）※A-00に依存
- A-03 受信画面（F04・F05・0件表示）※A-00に依存
- A-04 デモモード（F06）＋文言・デザイン仕上げ ※A-01〜A-03に依存
- A-05 統合・受け入れテスト（T01・T03・T04・T05＋T06ルート分離）※全てに依存

## 9. Gemini評価ルーブリック（合格条件）
配点：体験の成立25／仕様適合性25／UI（朝の優しさ・スマホ最適化）20／コード品質・保守性（データ層抽象化を含む）15／テスト・堅牢性15
合格：総合85点以上（適用項目の得点合計÷適用満点×100）、各項目70%以上、Issue固有の受入条件を全て満たす、自動テスト合格、重大不具合なし。
点数に関わらず不合格：応援URLから他人のメッセージ本文が読める、解禁前に本文が見える（デモモード経由を除く）、人からの応援の偽造、データ層を経由しない直接localStorageアクセスの混入。
