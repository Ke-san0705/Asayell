# アサエール 設計 v6（ラウンド6：仮説検証機能）

作成：2026-11-29（Startup Weekend 富士 4th 最終ピッチ当日）
対象リポジトリ：Ke-san0705/Asayell ／ 公開URL：https://ke-san0705.github.io/Asayell/

## 1. 目的

「人からの応援によって、朝の心理状態が変化するか」を測定できるようにする。
検証対象の想定ユーザーは入社1年目の新入社員。最終ピッチで仮説検証の仕組みそのものを提示できる状態にする。

## 2. 測るもの

受信前と受信後に、同じ3項目を5段階（1=まったくそう思わない〜5=とてもそう思う）で聞く。

1. 今日を迎えることが楽しみだ。
2. 自分を応援してくれる人がいると感じる。
3. 自分の未来を前向きに考えられる。

受信後のアンケートでは、加えて「継続利用意向」を5段階で聞く。
4. これからもアサエールを使いたい。

## 3. 体験フロー（受信画面 /o/:ownerToken）

1. 起床時刻到達後（またはデモモード）で受信画面を開く。
2. エール本文を見せる前に「受信前アンケート」を提示する。
   - 検証参加への同意文と同意チェックを必須とする（同意しない場合は保存しない）。
   - 「回答せずにエールを読む」導線を常時表示し、回答しなくてもエールは読める（必須条件）。
3. エールを1通ずつ読む（既存の体験は変えない）。
4. 最後まで読んだら「受信後アンケート」を提示する（3項目＋継続利用意向）。こちらも任意で、スキップできる。
5. 同じ目標（同一体験）では、受信前・受信後はそれぞれ1回だけ保存できる（重複集計防止）。回答済みの場合はアンケートを再表示しない。

待機画面（起床時刻より前に受信画面を開いた場合）は、届いているエールの件数を表示する（本文は見せない。既存の解禁制御を維持）。

## 4. データ設計（Supabase、計算無双プロジェクトに相乗り）

新規テーブル `asayell_survey_responses`（RLS有効、anon直接ポリシーなし、アクセスは全てRPC経由）。

- id uuid / goal_id uuid（asayell_goalsへの外部キー、cascade削除）
- phase text（'pre' / 'post'）
- is_demo boolean（デモ受信か、実際の時刻到達後の受信かを区別）
- q1, q2, q3 integer（1〜5）
- continue_intent integer（1〜5、postのみ）
- consent boolean（同意が取れた回答のみ保存するので常にtrue）
- created_at timestamptz
- 一意制約：(goal_id, phase) — 同一体験の重複保存をDB側でも防ぐ

RPC（いずれも security definer）：

- `asayell_save_survey_response(p_owner_token, p_phase, p_is_demo, p_q1, p_q2, p_q3, p_continue_intent, p_consent)`：同意がない場合は例外。重複は on conflict do nothing で無視する。
- `asayell_get_survey_status(p_owner_token)`：回答済みphaseの一覧を返す（UIの再表示防止用）。
- `asayell_get_message_count(p_owner_token)`：待機画面用に、届いているエール件数（visibleのみ）のみを返す。本文は返さない。
- `asayell_list_survey_responses()`：集計出力用。goal_id / phase / is_demo / q1〜q3 / continue_intent / created_at のみを返す。氏名・アカウント名・メッセージ本文・owner_token / support_token は絶対に含めない。

マイグレーション：`supabase/migrations/20261129000000_asayell_surveys.sql`（マル作成）。適用は本人がSQL Editorで実行する。適用前は実装PRのレビューは進めてよいが、実データでの受入確認は保留する。

## 5. CSV出力

- ルート `/export` に集計データ出力ページを置く（下部ナビには載せない）。
- `asayell_list_survey_responses` の結果をCSV形式でダウンロードできる。
- 列：goal_id, phase, is_demo, q1, q2, q3, continue_intent, created_at
- 氏名・メッセージ本文・本人専用トークンを含めない（RPC側で保証）。

## 6. 登録フォームの入力例（新入社員向け）

- 目標登録フォームに、入社1年目の新入社員向けの入力例を表示する（タイトルのプレースホルダと、例文のヒント表示）。
- 例文の方向性：「初めての商談、緊張するけど頑張る」「朝の満員電車に負けずに出社する」「先輩に質問できるようになる」など、仕事の朝に寄せたもの。
- 既存の入力項目・制約は変えない（ラウンド4.5で削除した詳細欄は復活させない）。

## 7. データ層

- UIは従来通り `AsayellRepository` インターフェース越しにのみアクセスする。直接localStorageアクセスは不合格。
- 追加メソッド：saveSurveyResponse / getSurveyStatus / getMessageCount / listSurveyResponses。
- SupabaseRepository はRPC呼び出しで実装。LocalRepository にも同等の実装を用意し、ローカルでもフローが動くようにする。

## 8. Issue構成

- R6-01：受信前・受信後アンケート＋継続利用意向（同意・スキップ・重複防止を含む受信画面フロー）
- R6-02：待機画面に届いているエール件数を表示（R6-01のマージ後に開始。受信画面が競合するため直列）
- R6-03：目標登録フォームに新入社員向け入力例を表示（独立）
- R6-04：CSV出力ページ /export（独立）
- R6-05：統合テストと公開確認（全件マージ後）

## 9. Gemini評価ルーブリック（ラウンド6）

配点：体験の成立25／仕様適合性25／UI（朝の優しさ・スマホ最適化）20／コード品質・保守性15／テスト・堅牢性15。
合格＝総合85以上・各項目70%以上。

不合格条件（点数無関係、従来分に追加）：
- 回答しないとエールが読めない作りになっている
- 同意なしにアンケート回答が保存される
- 同一体験で同じphaseの回答が重複保存される
- 集計データ（RPC・CSV）に氏名・アカウント名・メッセージ本文・トークンが含まれる
- デモ受信と実受信の区別（is_demo）が保存されていない
- 待機画面でエール本文が見える

## 10. やらないこと

- メールログイン（ラウンド6の対象外、後回し決定済み）
- 起床時通知
- 大規模なリファクタリング
- 既存デザインの変更（踏襲する）
